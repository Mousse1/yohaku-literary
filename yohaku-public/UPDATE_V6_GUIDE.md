# 余白。v6 — 作品内作品／階層目次の更新手順

## 何が変わるか

作品を「親作品 → 部・章 → 節・記事」の入れ子で配置できます。たとえば：

- 『エチカ』（作品集・目次グループ）
  - 第一部 神について（章グループ）
    - 定義／公理（本文を持つ作品）
    - 定理（本文を持つ作品）
  - 第二部 精神の本性と起源について（章グループ）

各項目が**別々の作品IDと個別URL**（`/works/<UUID>`）を持ちます。作者／入力・構成、カテゴリ、文献、数式、文字サイズ調整、承認・改訂履歴も維持します。

- 通常の作品本文は従来どおり **10～200,000文字**。
- 「作品集・部・章のグループ」の本文は **0～200,000文字**（空欄の目次を作れる）。
- 紹介文は従来どおり10～1000文字、作品名180文字以内。上限は変えていません。
- 親作品は「自分の作品」から選びます。他人の投稿を子作品にすることはできません。
- 作品の承認は従来どおり項目ごと。子を公開する前に、親から順番に承認してください。
- 公開済み作品の階層変更は「改訂版を書く」から申請します。承認前は元の親作品の下に残ります。
- どの親作品も、子が残っている間は削除できません。削除する際は先に子を整理してください。

## 更新前（重要）

1. Supabaseのデータをバックアップします。できれば非公開のテスト環境で確認してください。
2. v5までのデータベース移行が**全て成功済み**であることを確認します。新規Supabaseプロジェクトには旧 `schema.sql` → v2 → v4 → v5 → v6の順で適用してください。既存の本番DBで旧スキーマを再実行しないでください。
3. **先にSQL**を実行し、成功してから新しいフロントエンドを配備してください。SQL適用前にv6画面だけ配備すると、作品一覧・投稿が失敗します。

## 1. Supabaseの更新（既存作品は保持）

Supabase Dashboard → 対象プロジェクト → **SQL Editor → New query** を開きます。

`supabase/migrations/20261030_nested_works.sql` の全文を貼り付けて実行してください。ファイル末尾は `notify pgrst, 'reload schema';` です。エラーが出た場合は繰り返し実行せず、エラー行を確認して対応してください。

追加されるDB列：
- `public.works.parent_work_id` (任意、親作品ID)
- `public.works.order_index` (0～9999、同階層内での順番)
- `public.works.node_kind` (`work` / `collection`)

追加API：`public.save_work_v6`。旧 `save_work_v5` は残し、承認済み改訂を処理する `review_revision` とスナップショットの処理を更新します。Row Level Securityは維持し、匿名利用者は**その作品と全ての祖先が公開済みの場合のみ**作品を取得できます。

SQL実行後、次の読み取り専用のSQLで確認できます。

```sql
select column_name, data_type
from information_schema.columns
where table_schema='public' and table_name='works'
  and column_name in ('parent_work_id','order_index','node_kind')
order by column_name;

select proname from pg_proc
where proname in ('save_work_v6','is_published_in_hierarchy');
```

## 2. GitHub → Cloudflare Workersを更新

1. 本ZIPの `yohaku-public/` **内のファイル**を、GitHubで現在使用中の `yohaku-public/` に上書き反映します（既存ファイルのバックアップを推奨）。
2. Worker → Settings → Buildの **Root directory** は `package.json` のあるパスを使います。ZIPと同じフォルダ構成なら `yohaku-public` です。
3. Build command: `npm run build` / Output directory: `dist`（既存設定を維持）。
4. `VITE_SUPABASE_URL`・`VITE_SUPABASE_ANON_KEY` 等の**ビルド用環境変数は変更不要**。以前設定したものを維持してください。
5. GitHubへのコミット後にCloudflare Workers Buildsで再デプロイします。

既存の `public/_redirects` は追加しないでください。WorkersでのSPAフォールバックは `wrangler.jsonc` が担当します。

## 3. 操作手順（例：『エチカ』）

1. ログイン → 「作品を投稿」 → 種類「作品集・部・章のグループ」、タイトル「エチカ」、本文は空欄でも可。紹介文を10文字以上にし、作者「スピノザ」、入力／構成の名前を登録。審査へ提出。
2. 管理者が「エチカ」を承認して公開。
3. 「自分の作品」→『エチカ』→**「この中に作品を追加」** → 種類「作品集・部・章のグループ」、タイトル「第一部 神について」、紹介文を入力、提出 → 承認。
4. 「自分の作品」→「第一部 神について」→ **「この中に作品を追加」** → 種類「作品・本文」、タイトル「定義／公理」、本文を10文字以上入力 → 提出 → 承認。
5. 一般公開の『エチカ』を開くと「第一部 神について」、その下に「定義／公理」が**階層目次**として表示され、それぞれをクリックして固有URLで読めます。

## 4. 重要な注意

- 既存作品は最上位に残ります。必要なら「改訂版を書く」で既存作品の収録先を変更してください。
- 作品ごとに承認が必要です。親が審査待ちの間は子も公開できません。
- 未承認の子作品は匿名ユーザー向けの目次に表示されません。親を非公開にすると子も匿名閲覧できなくなります。
- 現版は目次インデックスを一度に最大1,000件取得します。投稿件数が増えたらサーバー側での階層ページングが必要です。
- **サンプル『エチカ』は未接続プレビュー専用の架空データ**で、Supabase本番へは投入しません。
- 章や節は独立した投稿として審査されるため、親作品が公開済みでも子作品の審査を省略しません。
- SQLは静的レビューのみ。本番DB・ブラウザでの動作検証は、運営者の環境で行ってください。
